# Project working rules

- Work and verify changes locally first. Rebuild or restart the affected Docker services, then inspect the actual storefront at `http://localhost:8080` and the API at `http://localhost:8000` when relevant.
- Confirm the changed behavior and its images/data render correctly in the local browser before pushing to `dev` or deploying to the VPS. Do not skip local verification.
- Add or update meaningful tests for every new feature or behavior change, and run the relevant checks before delivery.
- Keep storefront content and product data backend/database-driven. Do not hardcode business content into UI components; use reusable templates and render API data.
- **Environment parity is a project-wide rule:** develop the application as production-grade software while running it in pre-production. Preprod and production must use the same application code/artifact, service architecture, deployment workflow, and security controls. Moving from preprod to production should require configuration and environment-specific secrets only; never add a preprod-only code path or manual deployment process. Select domains, hosts, paths, and encrypted secret groups through validated environment/config/CLI inputs. Fail closed when production configuration is missing and never fall back to preprod credentials.
- **Deployment always follows three gated phases:** (1) develop and verify locally, including relevant tests and browser/API checks; (2) deploy to preprod only after local verification passes, then exercise it there; (3) promote to production only after preprod is stable and explicitly accepted. Production promotion uses the same tested revision/artifact and changes environment configuration/secrets only. Never skip a phase or deploy an unverified working tree.
- Coordinate backend work with Gemini through the selected work folder. Its `README.md`, `tasks.md`, `decisions.md`, `notes.md`, `coordination.md`, and exact task contract are the source of truth. `docs/handoffs.md` and `docs/coordination-status.md` are global indexes only; never put a second copy of an active contract or live task status there. Historical logs are preserved under `docs/archive/`.
- Persistent work tracking lives in `work/`: start with `work/INDEX.md`, then read only the active work item's `README.md`, `tasks.md`, `decisions.md`, and relevant task file. Before implementation, document a main work item and small verifiable subtasks. Maintain statuses (`Pending`, `In Progress`, `Completed`, `Blocked`), decisions, dependencies, and blockers. After meaningful work, update the task record and `work/INDEX.md` only if the high-level status changes. Keep `TASKS.md` as a pointer to the index, not a second task database.
- Every subtask handed across agents must have a pickup-ready contract in `work/<work-folder>/tasks/`, based on `work/TASK_TEMPLATE.md`. Include objective, context, in/out of scope, dependencies, relevant files, acceptance/tests, and the exact return handoff. Small same-agent subtasks may stay as concise checklist entries.
- Every work folder has a `coordination.md` that points to its active cross-agent task contracts, names the current owner, and records whether the handoff is waiting, active, returned, or blocked. Keep detailed handoff state in that work folder only. The global `docs/handoffs.md` is a short active-handoff registry linking to those files; global coordination status links to `work/INDEX.md` and the registry.
- Before beginning a Gemini task, provide the reusable rules in `work/GEMINI_WORKFLOW_PROMPT.md` and point Gemini to the one selected work folder and exact contract. Gemini marks only the assigned subtask `In Progress`, records meaningful decisions/blockers, runs acceptance checks, and updates that same task plus work-local notes/coordination before returning it. Do not assume Gemini has seen a chat prompt unless the repository contains the contract.
- Never repeat completed setup or asset work in a handoff. Explicitly list verified inputs and their exact paths/keys; if an asset is already uploaded and its public URL verified, the backend task is to update the database reference only unless the contract says otherwise.

- Shared coding skill guidance is configured in [SKILLS.md](SKILLS.md); use that single pointer when selecting a relevant skill.
