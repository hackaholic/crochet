# Authentication API — V1 contract

This is the canonical Sulocraft V1 authentication contract. Customer authentication supports Google, Facebook, and email magic links only. Phone numbers remain delivery contact data and are never credentials.

## Customer behavior

- Anyone can browse, add products to a guest cart, and complete checkout without signing in.
- Signing in merges the guest cart into the authenticated cart without losing items.
- Guest checkout requires name, email, phone, and shipping address. It does not create a permanent user.
- Every authentication provider creates the same secure server-side session cookie.
- The frontend never stores provider or session tokens in local storage.

## Endpoints

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/api/v1/auth/google` | Verify a Google ID token, link a verified identity, merge the guest cart, and create a session. |
| `POST` | `/api/v1/auth/facebook` | Verify a Facebook access token/profile, link a verified identity, merge the guest cart, and create a session. |
| `POST` | `/api/v1/auth/email/start` | Send a single-use magic link. Always return the same generic success response. |
| `GET` | `/api/v1/auth/email/verify?token=…&returnTo=…` | Consume a magic-link token, create/link the user, merge the guest cart, set the session cookie, and redirect safely. |
| `GET` | `/api/v1/auth/me` | Return the current user for a valid session. |
| `POST` | `/api/v1/auth/logout` | Revoke the current session and clear its cookie. |

The previous `/auth/phone/send-otp` and `/auth/phone/verify-otp` routes are removed from the V1 contract.

## Start email login

Request:

```json
{ "email": "customer@example.com" }
```

Response for valid, invalid, known, unknown, throttled, and suppressed addresses must not reveal account membership:

```json
{ "message": "If the email address is valid, a sign-in link has been sent." }
```

Use HTTP `202` for an accepted request. Rate-limit by normalized email and client address without changing the public response body.

## Verify email login

The email contains an HTTPS URL generated by the backend. Tokens must be cryptographically random, stored as a one-way hash, expire in 10–15 minutes, and be consumed once. Never log the raw token.

On success the backend:

1. invalidates the token atomically;
2. creates or links the `email` identity using the verified normalized email;
3. merges the browser guest cart into the user cart;
4. issues the normal HttpOnly session cookie;
5. redirects only to an allow-listed Sulocraft path.

Expired, invalid, and already-used links redirect to a generic frontend sign-in error. The response must not expose internal user IDs.

## Unified user and identity rules

`User` is the canonical customer. `UserIdentity` stores `google`, `facebook`, or `email` plus an immutable provider subject. A verified normalized email may link identities to the same user. Never auto-link using an unverified provider email.

Deterministic cart merge:

- retain all distinct variants;
- for duplicate variants, add quantities up to available inventory;
- preserve valid personalization as separate lines when personalization differs;
- return `cartMerged` in the auth response where the provider flow returns JSON.

## Sessions and security

- Cookies: HttpOnly, Secure in production, explicit SameSite policy, configured domain, and server-side revocation.
- OAuth: validate issuer, audience/app ID, expiry, provider state, verified email, and allowed redirect origins.
- Magic links: rate limiting, short expiry, single use, hashed storage, and generic errors.
- CSRF protection applies to cookie-authenticated mutations.
- Production must reject mock provider tokens and unsafe redirect URLs.

## Transactional email

Magic links use the shared email-provider abstraction and environment configuration. Production sender examples are `login@sulocraft.com`, `orders@sulocraft.com`, and `hello@sulocraft.com`, with SPF, DKIM, and DMARC configured. Business services must not depend directly on one vendor.

## Administration

Removing phone OTP must not remove administrative access. Administrators sign in through one of the supported V1 providers and receive the existing `ADMIN` role from backend-managed authorization data. Bootstrap the first administrator through an explicit seed/management operation using a verified email; never let frontend input assign roles.
